# Mentor snapshot cache

The four entry points are exported from `index.ts`:

- `readCachedMentor(bindings, principal, request, requestId?)` returns a normal bridge envelope for the thirteen data reads. It only reads the database and hashes a local cursor; it never calls HTTP. Writes and `attachments.download` must remain on the existing real-time service paths. Cached attachments already contain opaque browser handles: do not apply `projectLiveAttachments` a second time.
- `syncMentorAccount(bindings, principal, options?)` fetches complete due namespaces through the existing `callFlow` DTO/authorization boundary, then publishes them atomically. It returns `synced`, `not_due`, `busy`, `disabled`, `not_allowed`, `denied`, `failed`, or `superseded`. Individual source failures are safe result codes, not raw exceptions or source bodies.
- `runDueSync(bindings, options?)` discovers every active live Mentor account using its stored identity mapping and processes at most 20 per tick by default. Newly activated accounts need no environment edit. The optional internal `mentorUserId` selector supports a one-off operator run and never bypasses account/source authorization. It returns `{status:'ok'|'partial'|'disabled',accountsChecked,results}`. Results describe namespace attempts (up to two per account); the production runner synchronizes private then catalog independently, so catalog failure cannot prevent a complete private snapshot from publishing. A runner must inspect this status; a resolved promise does not necessarily mean every account synchronized.
- `invalidateMentorCache(bindings, principal)` keeps last-good data, marks both namespaces due now and fences any in-flight sync. A successful business write must not be reclassified as failed if queuing this refresh fails.

`MENTOR_CACHE_ENABLED` must be exactly `true`. Eligibility comes from active live Mentor accounts with the exact current account-to-User mapping; the obsolete `MENTOR_SYNC_ALLOWED_USER_IDS` setting is ignored, including stale or malformed values. `MENTOR_CACHE_PRIVATE_TTL_HOURS` defaults to24, `MENTOR_CACHE_CATALOG_TTL_HOURS` to48, and `MENTOR_CACHE_MAX_STALE_HOURS` to72. Values must be integer hours1–72 and refresh intervals cannot exceed the hard age. Hard age is absolute since the successful snapshot timestamp, not an extra72 hours after soft expiry. The read path also applies a newly reduced hard-age limit immediately.

Both namespaces use `(account_id, mentor_user_id, namespace)`. Private contains profile, balance and personalized ranking, all owned groups/details/reports/expenses, transactions, ticket lists/details and redemption history. Catalog contains only reward lists/details/options and is still scoped to the same identity; no global personalized catalog is shared. A namespace is one complete JSON document. Group report IDs are scoped by kind because source lists can reuse the same numeric ID.

Cold data returns `CACHE_PENDING`503. Soft-expired or write-invalidated last-good data remains readable with `bootstrap.dataSync.stale=true`. `dataSync` describes the private namespace; catalog has its own48-hour schedule. At the hard deadline reads return `CACHE_EXPIRED`503. A new report is absent until a complete replacement snapshot is published: its write acknowledgement is the immediate result, while cached get/list stay at the prior snapshot. There is no partial insert into cached history.

Every read rechecks the local active account, mode and exact Mentor mapping, then joins its snapshot with the current source-authorization tombstone. A definitive source `MENTOR_FORBIDDEN`, `OWNERSHIP_DENIED`, `BRIDGE_UNAUTHORIZED` during collection clears both identity-scoped snapshots and fences overlapping workers. A `RECORD_NOT_FOUND` race is an ordinary refresh failure, not a whole-account authorization denial. Ordinary source failures retain the whole prior snapshot and schedule a15-minute retry. Removed groups and all their reports/expenses disappear together on successful replacement. Attachment bytes are never cached; only the existing authorized metadata-handle table is populated during sync, and downloads still revalidate the source parent live.

The account lease lasts two minutes and is renewed before/after each source call. Publication is a fenced D1-style batch: first compare lease/token/invalidation version and active mapping, write all complete requested snapshots, then release the lease and update due times. The Node SQLite adapter must implement `batch` as an actual transaction with accurate `meta.changes`. A direct multi-namespace `syncMentorAccount` call publishes its requested set together; `runDueSync` deliberately calls it once per namespace to isolate catalog availability. An expired lease can be reclaimed after process restart; a superseded worker cannot publish. Invalidation races also discard the in-flight result. Positive-ID readback is not used as a substitute for this transaction.

Source pagination accepts only progressing canonical numeric last-ID cursors and ascending, nonduplicated IDs. Default bounds are40 pages/2000 list records,100 groups,500 tickets,500 rewards,1300 calls and8 MiB per snapshot. Exceeding a bound rejects the refresh instead of publishing a truncated collection. Calls are sequential and start at least1100 ms apart by default to respect the existing60-calls/minute bridge guard. Tests can inject synthetic `fetcher`, `now`, `sleep`, narrower limits, timings and namespaces; no production endpoint or secret is used in tests.

Local verification: `CLOUDFLARE_CF_FETCH_ENABLED=false node --experimental-strip-types --test --test-timeout=120000 tests/mentor-cache.integration.test.ts`. The suite runs the production migrations in temporary Miniflare/D1 and covers offline reads, identity isolation, TTLs, atomic rollback, record removal, authorization denial, source/cache cursors, invalidation, lease takeover/recovery and namespace scheduling. It does not validate real Flow performance, source permissions, deployment scheduling or production secrets.

Source-call failures emit only the fixed `mentor_cache_source_read_failed` event with operation, generated requestId, safe code and HTTP status. No raw exception, message, URL, headers, body or record values are logged.
