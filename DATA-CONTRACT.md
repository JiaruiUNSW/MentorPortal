# Mentor Portal data contract — v1.0

The canonical TypeScript contract is `lib/contracts.ts`. Every page calls `POST /api/mentor` with `{operation,payload,idempotencyKey?}`. All POSTs require a signed-in cookie, exact Origin and `X-CSRF-Token` returned by `GET /api/auth/session`. Every mutation requires a fresh UUID idempotency key; retries of the same intended operation must reuse it. Responses use `{schemaVersion:"1.0",requestId,ok,data?,error?:{code,message,retryable},replayed?}`. Never submit actor IDs, roles, list names, URLs or query expressions. IDs are opaque strings; the live adapter resolves SharePoint IDs. `actor.userId` is the server-resolved positive numeric Mentor User ID.

Read operations: `bootstrap`, `groups.list/get`, `reports.list/get`, `balance.get`, `transactions.list`, `rewards.list/get`, `profile.get`, `tickets.list/get`, `redemptions.list`. List results are `{items,nextCursor}`. `groups.get` returns `{group,mentees,reports,expenses,tasks}`. `profile.get` returns `{profile,choices}`. `rewards.get` returns `{reward,options}`. Pass no cursor for the first page; cursors are opaque and must not be constructed. Page size defaults to 25, maximum 50.

Writes: `attendance.save`, `reports.week1.save`, `reports.meetup.save`, `reports.completion.save`, `expenses.save`, `attachments.upload/download/delete`, `profile.update`, `redemptions.create`, `tickets.create/update`. `attachments.download` is a read operation and does not need an idempotency key. Existing records require their returned `version` as `expectedVersion`; a conflict requires reloading before editing. Report saves default to `submit:true`. `submit:false` preserves a portal draft in demo; this is a portal feature, not an existing SharePoint draft column. Final meet-up submission requires at least one attached photograph; expense submission requires a receipt. Ticket status and staff responses are read-only; Closed tickets cannot be edited.

Upload staging: call `attachments.upload` with `{parentKind:"meetupReport"|"expense"|"ticket",groupId?,parentId?,expectedVersion?,file:{fileName,mimeType,contentBase64}}`. New report/expense uploads require an owned groupId. New ticket uploads are bound to the account until ticket creation. Use returned `attachment.id` values in the corresponding save's `attachmentIds`. Existing-parent uploads require `expectedVersion`. A staged upload is permanently bound to its parent on save. Allowed files: JPEG (.jpg/.jpeg), PNG (.png), HEIC (.heic), HEIF (.heif), PDF (.pdf); MIME, extension and signature must agree, maximum 5 MiB, maximum five files per record, maximum 20 unattached uploads per account. Final meet-up reports require JPEG/PNG/HEIC/HEIF. HEIC/HEIF use validated ISO-BMFF ftyp brands and download-only delivery; the two source allowlists are consolidated so both supported phone photo formats can be used consistently. `attachments.download` returns an authenticated same-origin `downloadUrl`; `GET /api/files/:id` checks session and ownership again and uses attachment disposition. No raw object keys or arbitrary remote URLs reach the browser.

Profile identity (id/name/email) is read-only. Editable source mappings: country→Country, phoneNumber→PhoneNumber, communicationChannels→IsWeChatWA, programs→Program, stream→StreaminDip, otherStream→Stream_x002d_Others, wwcc→WWCC, **wwccExpiryDate→WWCCExpDate**, dateOfBirth→DoB. `under18` is validation-only. User.Valid=1 and IsRead=true, current assignment ownership and source statuses must be revalidated by each live adapter. Role and identity fields are never writable.

Demo mode is explicit `PORTAL_MODE=demo`, returns `previewLabel:"Synthetic preview data — not connected to SharePoint"`, and stores synthetic data separately for each account in D1. It never sends requests to Flow URLs. Cedar, Banksia and Wattle are synthetic Round 3 2026 fixtures. All preview saves, tickets, attendance and redemptions persist across refresh. A pending redemption reserves available preview credit once and stays pending; it does not simulate approval or fulfillment. Live mode is the fail-closed default and never falls back to demo.

Live dispatch uses one fixed server binding per operation family (`MENTOR_READ_URL`, `MENTOR_ATTENDANCE_URL`, `MENTOR_REPORT_URL`, `MENTOR_EXPENSE_URL`, `MENTOR_ATTACHMENT_URL`, `MENTOR_PROFILE_URL`, `MENTOR_REDEEM_URL`, `MENTOR_TICKET_URL`) plus `MENTOR_BRIDGE_KEY`. HTTPS endpoints must be Power Automate/Logic Apps hosts. The server creates `{schemaVersion:"1.0",requestId,operation,actor:{userId,portalAccountId},payload,idempotencyKey?}` and authenticates with `X-Mentor-Bridge-Key` and `X-Mentor-Request-Id` matching the envelope request ID. Configuring a URL does not certify that the adapter implements validation, ownership, mapping, deduplication or asynchronous approval. Draft templates are not production-ready endpoints. Activating live requires implementing and independently verifying those adapters. Calls have deadlines, redirects are rejected, upstream error text and secrets are never surfaced, and writes are never blindly retried after an unknown outcome.

D1 request rows have a unique account/mode/idempotency key and a canonical payload hash. Conflicting reuse is rejected. Demo business changes, successful response and audit metadata are committed together using one D1 batch with revision and lease guards; there are no unsupported manual BEGIN/COMMIT claims. Concurrent updates either commit once or return a retryable conflict. Interrupted pending demo writes can be resumed only after an expired lease. Live timeouts and malformed success responses remain uncertain and must be reconciled by the same adapter idempotency key; a fresh browser key must not be used to repeat an uncertain intent.

R2 and D1 are not one transaction. File metadata starts staging; byte failures are marked failed. Ready but unattached files may remain after a cancelled form. Attachment audit and parent binding are persisted; deletion marks metadata before deleting bytes and can be resumed if storage fails. An object may remain orphaned after a partial storage error and must be removed by an operational cleanup procedure after reference checks. No background cleanup has been claimed or silently enabled.

## Current activation limits and verified boundary

The shipped preview implements all listed operations with D1 and R2. Its six task entries cover first attendance, Week 1, two meet-ups, final attendance and completion. Final attendance is a preview task marker derived from completion; it is not evidence of a live AttendanceUpdate flow execution. Source credit criteria are displayed from v548; the preview leaderboard is synthetic and no criterion automatically issues real credit.

Live mode is an adapter integration boundary, **not an activated SharePoint integration**. Every HTTP adapter still needs its documented identity/ownership checks, source-field mapping, source ETag checks and idempotency ledger implementation. The existing PowerApps V2 flows cannot be used as these HTTP URLs unchanged. The following limits are intentional:

- `submit:false` is supported only in demo. No live draft table is provisioned, and live draft requests return `DRAFT_NOT_CONFIGURED` before dispatch.
- Live `reports.list` requires `groupId`; the adapter returns a bounded aggregate of at most 100 reports with `nextCursor:null`. It does not combine independent list cursors. Other list cursor values remain opaque to the browser.
- Existing live report `submissionState` and expense `processingStatus` can be `unknown`; source review flags do not prove final workflow/receipt completion. These are not normalized into success.
- `redemptions.create/list` require a source request-ledger schema and verified asynchronous approval processing that the adapter drafts do not yet provide. The server's preview pending/reservation behavior is not an approval integration.
- Live attachment mutations require the adapter concurrency review gate to be completed. R2 staging does not establish atomicity with SharePoint. A successful source save followed by uncertain metadata/file mapping returns `PARTIAL_WRITE` and must be reconciled using the same request reference.
- Live attachment IDs are held in a server-only `source_attachment_id` field. Browser handles are account-bound; every file read revalidates source parent ownership. Source listings may have `sizeBytes:null`; actual download bytes are bounded and validated. New files on a single final live submission are limited to 10 MiB total, with the 5 MiB/file and five-file caps still applying.
- New mutation intents are limited atomically to 30 per account per minute; replaying an existing key does not consume another intent. Live outbound adapter calls (including authorization reads) are limited to 60 per account per minute. The D1 audit records identifiers/operation/outcome only, not request bodies, WWCC, date of birth, attachment contents or bridge credentials.

Validated locally with the production Drizzle migrations in an actual Miniflare Worker, D1 and R2 runtime: 19 integration tests pass. Run `CLOUDFLARE_CF_FETCH_ENABLED=false node --experimental-strip-types --test --test-timeout=120000 tests/mentor.integration.test.ts` (loopback access is required). TypeScript and scoped ESLint also pass. These tests do not certify a configured external Flow, delivery of approvals, receipt processing or SharePoint mutations.

Live replay hardening: cached writes reauthorize the exact created ticket/report or stored attachment parent before returning cached data. Explicit adapter `REQUEST_IN_PROGRESS` acknowledgements are kept as `upstream_pending`, not terminal failures; after a three-second lease, a user-initiated retry can query the same adapter with the original requestId/idempotency key. Transport ambiguity remains `uncertain` and is never resent. Every uncertainty or in-progress response preserves the original recovery requestId.

Historical Flow attachment reads accept up to 50 entries per record, filenames up to 255 characters and parent-scoped source handles up to 2048 base64url characters. Source handles are converted to short account-bound D1 IDs before browser delivery; new uploads remain capped at five files with 150-character filenames. Historical metadata can describe a larger file, but actual binary delivery remains bounded to 5 MiB and checked by MIME/extension/signature. Live forwarded files receive `X-Mentor-Files-Validated-SHA256` only after every forwarded file passes server validation; its value equals the canonical payload SHA-256 header. HEIC/HEIF are validated by ISO-BMFF ftyp brand before forwarding or download delivery. Profile `preferredName` is the source DisplayName alias; source User.Title is the governed zID and must never be interpreted as a preferred name.

Cross-contract regression fixtures are checked in at `tests/fixtures/flow-contract-*.json`, with SHA-256 provenance in `flow-contract-manifest.json`. Fifteen sanitized response fixtures were generated by evaluating the native Flow DTO projection expressions against synthetic SharePoint rows; they are not tenant captures or an execution of the Flow runtime. Tests run from this standalone checkout, validate all generated responses, cover 50 historical attachments/255-character Unicode filenames/1010-character source handles, verify opaque browser handles and enforce the generated native header schema. Binary fixtures verify PNG and HEIC/HEIF signature handling; the HEIC/HEIF bytes are signature-test containers, not renderable photographs. Configured bridge keys must satisfy the native header contract of 32–512 printable non-whitespace ASCII characters.
